# 项目文档规范

目标：**每个事实只写在一处，每类文档只有一个位置，临时的东西用完就删。** 文档乱、重复、过时，主要是因为不同生命周期的内容混在一起，以及写之前没有先找已有的。

## 先判断项目有没有启用

项目根目录有 `.claude/project-docs.json` 就是已启用，按本规范执行。

没有这个文件时：不要自作主张套用这套目录。项目有自己的文档规范就按它的来；没有的话，照常完成用户的请求，并提一句可以用 `/project-docs:docs-init` 启用。

## 写之前：这个内容该不该成为文档

| 想写的内容 | 去哪 |
| --- | --- |
| 功能是什么、需求是什么、边界在哪 | `docs/specs/<功能>.md` |
| 这件事打算怎么做、分几步 | `docs/plans/<主题>.md` |
| 为什么选 A 不选 B | `docs/decisions/NNNN-<标题>.md` |
| 模块怎么分、数据怎么流 | `docs/architecture.md` |
| 面向用户的版本变化 | `CHANGELOG.md`（仅发版的项目，见下文） |
| 工作总结、改动说明、分析报告、调研结论 | **不写文件**：直接在回复里说，或写进 commit message |
| Bug、任务、待办 | **提 issue**，不写文档（项目没有 issue 系统时见下文） |
| 代码里能看出来的：参数、字段、目录结构 | **不写** |

没有被用户要求时，不要主动创建文档。完成一项工作后的说明属于回复，不属于仓库。

## 四类文档

### specs：功能与需求

一个功能一个文件，长期保留，原地更新。**需求和功能是同一个文件**：

- 需求阶段：新建文件，`status: planned`，写想要什么。
- 做完以后：改成 `status: shipped`，把内容改成实际行为。不另写一份"功能文档"。
- 下线以后：改成 `status: deprecated`，第一行写原因；确认没人需要后删除。

```markdown
---
status: planned
scope: 订单导出为 Excel；不含导入，不含报表
---

# 订单导出

## 做什么

## 为什么

## 不做什么
```

元信息只有这两个字段，都是必填。`scope` 用来判断一段新内容该不该写进这个文件。负责人、更新日期不要写，git 记录里有。

只描述现在是什么，不写历史过程；过程在 git 记录和决策记录里。

### plans：进行中的计划

临时文档。做一件需要多步的事时才写，写目标、步骤和完成标准。

**做完必须删**：

1. 有长期价值的结论并入对应的 spec 或 `architecture.md`。
2. "为什么这么选"值得留下的，写成一条决策记录。
3. 删除计划文件。

不做了的计划也直接删除。不要留着"已完成"的计划，过时文档大多是没删的计划。

### decisions：决策记录

一个决策一个文件，文件名 `NNNN-标题.md`，编号接着已有的最大编号，永不复用。写完不再修改；决策被推翻时新建一条，并在旧文件第一行写"已被 NNNN 取代"。

```markdown
# 0003 导出改为异步任务

日期：2026-11-25

## 背景

## 决定

## 放弃的方案

## 影响
```

只记有分量、以后会有人问"当时为什么"的决定，日常实现细节不记。

### architecture.md：架构

一个文件，描述现状：模块划分、数据流、关键约束。超过约 500 行再按子系统拆到 `docs/architecture/` 下，并让用户把这个位置加进配置的 `allow`。

## CHANGELOG.md：更新日志

**只有发版给用户的项目才需要**；没有版本号、持续部署的项目不要建。项目没有这个文件时不要主动创建，先问用户。

位置是发布单元的根目录：单项目在仓库根，多应用仓库在各应用目录下。一个发布单元只有一份，文件名固定为 `CHANGELOG.md`，不用 `HISTORY.md`、`RELEASES.md` 之类的名字，也不放进 `docs/`（构建和发布工具通常按固定路径读它）。

```markdown
## 1.4.0

### 新增

- 订单列表支持导出为 Excel

### 修复

- 验证码过期后仍可登录
```

- **只写用户能感知的变化。** 重构、测试、内部清理、依赖升级不写；用户不会注意到的小调整也不写。
- **按版本倒序，每个版本下只分四类**：新增、变更、修复、移除。没有内容的类别不写标题。
- **同主题合并成一条。** 加之前先读当前版本那一节，能并进已有条目就不新增一行；一个版本保持在几行以内。
- **已发布的版本不再改动。** 新变化写进最上面未发布的版本；当前版本已经发布时，先开一个新版本的小节。版本号是否已发布、何时升版本，按项目自己的发布流程判断，不确定就问用户。
- **不是每次提交都要记。** 改动的原因和细节在 commit message 里，更新日志只写结果，不写内部实现、文件名或敏感信息。

项目自己对更新日志有更具体的规定时（标题格式、语言、发布脚本的要求），以项目的为准。

## 写入规则

1. **先搜后写。** 读 `docs/README.md` 索引，再在 `docs/` 里搜关键词。已有相关文档就原地更新，不新建。
2. **一个事实只写一处。** 别处需要时写链接，不复制内容。
3. **只在允许的位置新建。** 不创建 `NOTES.md`、`SUMMARY.md`、`TODO.md`、`xxx-v2.md`、`xxx-new.md`，不在源码目录里放说明文档。包的 `README.md` 只写这个包是什么、怎么启动。
4. **改代码让文档失效时，同一次提交里改文档。**
5. **不确定该放哪、或者和已有文档是否重复时，先问用户。**
6. **改完更新索引并检查：**

   ```bash
   node scripts/check-docs.mjs --index
   node scripts/check-docs.mjs --check
   ```

   项目里没有 `scripts/check-docs.mjs` 时，用 `node "${CLAUDE_SKILL_DIR}/scripts/check-docs.mjs"`。`docs/README.md` 里的索引区块由脚本生成，不要手改。

## 没有 issue 系统的项目

Bug 和任务放 `docs/issues/`，一条一个文件，文件名用简短描述。关闭后直接删除，原因和修法写进修复它的 commit message。不要用一个大文件记所有条目。

## 自动检查

这个插件带一个 hook：在已启用的项目里，要在允许位置之外新建 `.md` 时会被拦截。收到 `[project-docs]` 反馈时：

- 按提示把内容写到正确位置，或者改为直接在回复里说。
- **不要自己修改 `.claude/project-docs.json` 来绕过。** 确实需要一个新位置时，向用户说明理由，由用户决定是否加进 `allow`。

修改已有的文件不会被拦截。

## 项目配置

`.claude/project-docs.json`：

```json
{
  "disabled": false,
  "docsDir": "docs",
  "allow": ["apps/*/docs/fixtures/**", "content/**"],
  "ignore": ["server/.github/**"],
  "planStaleDays": 30
}
```

- `allow`：额外允许放 `.md` 的位置（glob，相对项目根）。
- `ignore`：完全不检查的位置，例如第三方生成的文件。
- `planStaleDays`：计划超过多少天没动就在检查时提醒。

`docs/` 之外默认允许：各级 `README.md`、`CHANGELOG.md`、`CLAUDE.md`、`AGENTS.md`，根目录的 `LICENSE.md`、`CONTRIBUTING.md`、`SECURITY.md`、`CODE_OF_CONDUCT.md`，以及 `.claude/`、`.github/` 下的文件。

## 整理已有项目的文档

用户要求整理文档，或在已有项目里启用本规范时，用 `/project-docs:docs-audit`。原则：先出清单给用户确认，确认之前不移动、不删除任何文件。
